# 练习：把 Agent 问题卡片迁移到 Lynx

状态：仅定义学习任务，尚未实现或验证。

目标：选一个自己熟悉的小功能，逐步验证纯业务逻辑、UI、网络与宿主能力的边界。用个人编写的示例数据与代码完成，不复制公司源码或内部协议到公开仓库。

实际经历以 H5 / Web 为主，先参考 [项目背景](../notes/project-context.md)。Agent 的问题卡片、Agent 的音色交互卡、通用 VoicePicker 是不同对象；本练习先选定其中一种，不把试听、本地选择和服务端确认合并成同一个状态。

本次不创建应用或启动服务。进入编码阶段时再按选定的包管理器创建练习工程并记录锁文件；本地服务由用户启动，页面实测需用户明确要求。

## 阶段 A：先把原有业务讲清楚

先结合实际代码讲解，再在学习过程中逐步讨论以下内容；不要求先独立回答历史追问才能继续：

1. 卡片属于哪个会话、任务和交互？前端用哪些标识定位它？
2. 用户可操作、正在提交、结果未知、已经确认、任务继续执行，分别如何表达？
3. 哪个事件或查询结果才说明用户的输入已被接受？
4. 前端负责哪些防护，服务端需要保证哪些行为？
5. 切换项目、后台恢复或重新打开页面后，如何知道该继续展示什么？

产物：一份时序说明和状态转换表，可在讲解中共同整理，并注明独立完成、共同推导或提示后完成的范围；这一步不作为继续上课的前置考试。

## 阶段 B：实现不依赖 UI 的业务核心

使用自定义的公开示例协议，不假定它与线上协议一致。

- 设计 `Task`、`InteractionCard`、提交命令和事件类型。
- 将事件归并写成可独立调用的纯函数，明确版本 / 序号 / ID 的职责。
- 让传输层提供订阅、提交、回执查询、取消订阅等抽象，不在核心逻辑中直接读写 DOM。
- 为未知事件保留明确的兼容或拒绝策略。

产物：TS 核心代码和有意义的异常序列测试。阶段 A、B 也是现场编码训练的一部分，应记录自己独立完成与使用提示的范围。

## 阶段 C：接入 ReactLynx UI

- 使用 Lynx 元素呈现问题、选项、编辑 / 选择状态及反馈。
- 用后台线程事件处理和生命周期接入业务，不在渲染函数里执行请求或注册监听。
- 页面离开时清理订阅；对不支持中止的操作，阻止迟到结果污染新页面。
- 先用 Mock 传输与明确的固定事件序列运行，不把演示当成真实 Agent 生成成功。

产物：实际运行记录，包括依赖版本、平台、Explorer / 宿主、复现步骤和看到的结果。未运行时仅登记“代码已编写”。

## 阶段 D：核对真实网络与原生模块

网络和原生能力分开做，分别记录结果：

- 网络：核对请求、流式响应、重连、鉴权、前后台行为；确认目标运行环境能否使用原先的 SSE 客户端，必要时做传输适配。
- 原生：先选低风险的读取宿主信息等能力，按官方接口实现 / 接入模块；再考虑外跳与媒体能力。类型声明、Mock、真正宿主模块三者分开记录。
- 失败：保留不可用、取消、超时与业务拒绝的区别。超时后的重试策略按操作语义决定。

没有可用宿主或真实服务时，先交付接口设计和已验证的纯逻辑，剩余项标注“未验证”，不通过反复启动服务解决。

## 必须能解释和回放的场景

以下是练习验收要求，不是当前生产实现的描述。

| 输入 / 故障 | 验收问题 |
| --- | --- |
| 同一卡片事件被重复投递 | 如何避免出现两张卡片或状态重复推进？ |
| 用户快速连续点击提交 | 前端防护与服务端幂等分别保证什么？ |
| 提交到达服务端，但响应丢失 | 如何区分“结果未知”和“提交失败”，如何补查？ |
| 断开 SSE，但任务继续运行 | 为什么不能直接把任务标记完成或失败？ |
| 实时事件比历史快照新 | 如何决定合并顺序，避免状态倒退？ |
| 切到项目 B 后收到 A 的事件 | 如何隔离任务与页面状态？ |
| 页面销毁后收到宿主回调 | 如何清理请求并丢弃过期结果？ |
| 用户修改答案时收到确认事件 | 本地草稿与服务端确认状态如何协调？ |
